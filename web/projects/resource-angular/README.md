# @impulseframework/resource-angular

**@impulseframework/resource-angular** is the Angular binding of [`@impulseframework/resource`](../resource/README.md), the framework-neutral client for generated APIs. It is a comprehensive Angular library designed to provide a consistent and configurable foundation for building enterprise-level data-driven applications. By defining a configuration, you can dynamically generate entire application pages.

## Core Features

- **Dynamic Page Generation**: Define a `resourceConfig` to dynamically render components and build complex layouts. For example, the `resource-resolver` can switch between components based on your data.
- **Authentication & Authorization**: A set of services and guards for managing user authentication and permissions.
- **Utility Functions**: A set of helper functions for various tasks, such as data manipulation and request customization. Also included are tools for handling PATCH requests per the JSON Patch standard [RFC 6902](https://tools.ietf.org/html/rfc6902).

## Getting Started

To install it in your project, run the following command:

```bash
npm install @impulseframework/resource @impulseframework/resource-angular
```

`@impulseframework/resource` is a peer dependency: the application installs it once and both the generated client and this library resolve the same copy.

An application built on the library runs without zone.js, Angular's default since version 21, as the skeletons' applications and Lodestar do. The page is drawn again when a signal a template reads changes, when an input changes, or when the template handles an event, and not because a timer or a request finished. A component that changes a plain field from a timer, from a subscription or after an `await` therefore holds the value in a signal, or calls `ChangeDetectorRef.markForCheck()`.

Then import the library's stylesheet once, from the application's global styles (`src/styles.scss`):

```scss
@use '@impulseframework/resource-angular/styles';
```

The form components request its classes by name — the twelve-column field grid, the read-only and edit-mode treatments, the heading row that stays at the top — and it declares the color tokens the components draw with, which the application's theme sets (see Theming below). A list names every element it draws for itself (`impulse-resource-list-…`: its title is `impulse-resource-list-title`, a notice `impulse-resource-list-notice`) and requests none of the sheet's classes: it reads the tokens, and the switch for sticky headers (`--sticky-headers`). Without the import, fields lose their grid and section labels lose their styling.

Those classes have plain names (`.resource`, `.field`, `.row`, `.col-1` to `.col-12`, `.readonly-field`, `.hidden-field`, `.resource-container`, `.form-edit-mode`, `.header-container`) and the sheet is global, so it styles every element of the application that carries one of them, inside any component. A component of your own that draws something else gives its elements other names: a table cell named `resource` would be laid out as a form's flex row.

The stylesheet also brings the fonts the components render in, served by the application itself: Roboto in the three weights the Material typography uses (300, 400, 500; the latin and latin-ext subsets) and the filled Material Icons, as files of this package the application's build carries into its bundle as same-origin assets. The application's `index.html` carries no Google Fonts link and its content security policy no font host (`style-src` and `font-src` stay at `'self'`): a progressive web app's service worker fetches the page's requests under the policy delivered with its own script, whose `connect-src` names no font host, so a third-party font fails on every worker-controlled load, while a same-origin font is fetched under `connect-src 'self'` and cached by the worker's asset group, so the application renders offline and during an outage. The Material typography tokens, which the prebuilt themes set to `Roboto` alone, get a fallback chain (`Roboto, 'Helvetica Neue', Arial, sans-serif`), so a font that fails to load never leaves a component in the browser's serif default. An icon is never drawn as the letters of its name. An icon is one glyph of the icon font, written in the page as its name (`search`, `filter_alt`), and until the font has arrived a browser has only those letters: the font's `display: block` has it draw nothing in their place for three seconds, and after that the name, cut off at the icon's box. So `provideTheme` (`@impulseframework/resource-angular/ui-theme`) asks for the icon font as the application starts, before any icon is on the page, and the root element carries the class `awaits-icon-font` for as long as the font is on its way, however long that is; under it the stylesheet draws no icon, in a list, the menu bar, a button or a page of the application's own (`.awaits-icon-font .material-icons`). Each icon keeps its place, so nothing moves when the font arrives. A font that fails is not on its way: the class comes off, and the browser draws the names in other letters. An application that does not call `provideTheme` keeps the browser's own three seconds and no more. An application that wants the fonts alone imports `@impulseframework/resource-angular/styles/fonts`. The outlined icon set is not shipped; a component that needs it adds it here.

## Theming

The look of the components is the application's Material theme plus a small set of color tokens the library reads. An application themes the library in two steps: it defines a Material theme, and it hands the library's frame to that theme. A root that does neither keeps the look the library has always had.

**The Material theme** colors every Material control the components compose: the buttons, fields, tables, menus and dialogs. The skeletons define it in `theme.scss` with Angular Material's `mat.theme`, from a palette, a type face and a density, and name that file in `angular.json` in place of a prebuilt stylesheet (a prebuilt one, `@angular/material/prebuilt-themes/azure-blue.css`, is the same thing with a fixed palette):

```scss
@use '@angular/material' as mat;
@use '@impulseframework/resource-angular/theme';

html {
  color-scheme: light;
  @include mat.theme(
    (
      color: (
        primary: mat.$azure-palette,
        tertiary: mat.$blue-palette,
      ),
      typography: Roboto,
      density: 0,
    )
  );
}
```

**The library's frame** is what the components draw themselves: the navigation's links, headers and active bar, a section's border and label, a notice's border and background, a dialog's row separators, the unsaved-changes word. Each of those colors is a CSS variable the component reads, declared in the `styles` sheet with the library's own color as its default, inside a cascade layer (`impulse-defaults`) so that any declaration outside it wins. The `theme` sheet, the second `@use` above, sets every one of them from the Material system tokens the theme emits, so the frame follows the theme's roles: primary for what invites a click, error for what warns, the surface and outline roles for the rest. Change the palette and every surface follows; set a token after the theme sheet to override one place. The tokens, with their defaults and what the theme sheet sets them to:

The variables the sheet exposed before the tokens stay: `--default-blue` (a form in edit mode) and `--app-background-color` (a container's background) are set by the theme sheet too, from `--mat-sys-primary` and `--mat-sys-surface`; `--layout-label-background-color` and its presets, `--form-edit-mode-bg`, `--underline-fields` and `--sticky-headers` are switches the application flips, not colors the theme decides; the presets that name a surface (`--layout-label-background-white`, the default, `--layout-label-background-off-white` and `--layout-label-background-gray`) are set by the theme sheet from `--mat-sys-surface`, `--mat-sys-surface-container-low` and `--mat-sys-surface-container-highest`, so a section's label keeps its contrast in the dark theme whichever the application picks. The gray preset was first named `--layout-label-background-grey`: that name is kept for applications that set it, as the value of `--layout-label-background-gray`, and a stylesheet that reads it keeps the look it had. The components also read Material's own tokens directly where one fits (`--mat-sys-outline-variant` for a grid line, `--mat-sys-error` for a refusal), each with a literal fallback that applies only on a page with no Material theme at all. A spec in the library holds this contract: every token a component reads is declared with a default, the theme sheet sets every one of them, and no component stylesheet carries a literal color of its own.

**The titles.** The title of a page and the title of a section of it (a list under a row, a create form, a panel) are drawn at two sizes the `styles` sheet declares beside the colors, in the same layer: `--impulse-page-title-size`, 32 pixels, and `--impulse-section-title-size`, 24. On a phone, the width at which the frame's bar folds its menus away (599.98 pixels and under), they are 24 and 20, so a section's title is under its page's at every width. They are lengths, not colors: the theme sheet leaves them alone, an application sets one on `:root` after the `styles` sheet to change it (for every width: to keep a phone's size of its own, it sets that one again under the same `max-width: 599.98px` query), and the spec that holds the color contract holds these four numbers too. A title longer than its line breaks, inside a word where it must, and never runs past the edge of the page. A title shares its row with what the page offers beside it, a list's buttons or a row's Edit, Actions and close buttons: beside the title, sharing the rest of its line as they always have with the last of them at the far end, while they fit that line, and on the next line, again with the last at the far end, where they do not, wrapping again among themselves. So on a narrow screen the buttons are under the title, never over it and never past the page's edge, each with its icon and its words. The rule is written once (`styles/_headings.scss`) and the list page, a row's own page and the create form include it; a list's heading row is as wide as the list under it and no wider, the indent of its title inside that width; on a row's own page the row's view draws the page's title in that row, handed it by the page, and the view is drawn on every page that holds anything, so a page of lists alone and one whose first part is a component of the application's have their title drawn by the view too. A page draws its title itself in three cases: its row's view is folded into a panel, which has a title of its own; it holds nothing, no field and no part under the row, so no view is drawn; its configuration is not a row view's (an array's). It draws it in a row of its own above what the page holds, in the page's flow: the row is as tall as the title needs, 48 pixels for a title of one line, so a title of two lines moves what follows down and is never laid over it. Where the application turns sticky headers on (`--sticky-headers`), that row stays at the top of what scrolls, as the heading row of a view, a list and a create form does. Every one of those rows is drawn on the surface the page sits on (`--impulse-surface`, one rule, `covers` in `styles/_headings.scss`), so what scrolls under a row that stays at the top is covered and never shows through its title or its buttons; the heading row of a view or a list folded into a panel sits on the panel and is left as the panel draws it.

**A choice for the person.** An application that offers a choice of looks keeps the Material theme as above and lets the person pick Light, Dark or Match my device, and one of the palettes it offers, from `<impulse-theme-picker>` (`@impulseframework/resource-angular/ui-theme`) on whichever page keeps their own settings. `ThemeService` applies the choice to the root element, `color-scheme` as an inline style (the theme emits both values of every token, so the one property flips the page; for Match my device it is `light dark`, under which the browser draws whichever the device is set to and follows a change of that setting while the page is open) and `data-palette`, and remembers it in the browser's local storage (`impulse-theme`), so the login page honors it before sign-in and the next visit starts with it. Where the application places the frame (`provideFrame`), the look is kept with the person's account too, so it follows them to another device: when a person's session is first checked on a page the frame applies the look the account holds (`SessionInfo.look`) and remembers it in the browser, and it writes the person's next change to the account (`api.auth.changeLook`). The account's look is taken once for each sign-in: a later read of the session, the keepalive's among them, takes nothing back, so a change made on another device is seen at the next visit. A change writes the whole look as the page shows it, one write at a time in the order the changes were made; a write the server refuses or that does not reach it is dropped, and the page keeps the look. An account that holds no look takes none from the browser, since a browser several people share would hand one person's look to the next; what such a person then picks is kept with what the page was showing. An impersonated session neither takes the look of the person it acts as nor writes one for them. An application that draws its own shell injects `AccountLook` (`@impulseframework/resource-angular/auth-frame`) once to get the same. The application names its palettes twice, by the same ids: to `provideTheme` in its providers, and to the theme sheet's `palettes` mixin in `theme.scss`, which emits the first palette's theme on `html` (the look where no choice was made) and every palette's color tokens under `html[data-palette='<id>']`, with its primary color on `[data-impulse-swatch='<id>']` for the picker's swatch. The `palettes` sheet carries a Workspace palette ready-made, generated from Google's blue and green with Material's theme-color schematic; Angular Material's own (`mat.$azure-palette`, `mat.$violet-palette`, ...) are the rest of the choice. An application that offers one palette, or none, hands `provideTheme` no palettes and the picker offers Light, Dark and Match my device alone. An application's own stylesheets follow the choice as far as they read the Material tokens (`var(--mat-sys-surface)` for a page background, `var(--mat-sys-outline-variant)` for a hairline); a literal color stays what it is in dark.

```ts
provideTheme({
  palettes: [
    { id: 'blue', label: 'Blue' },
    { id: 'workspace', label: 'Workspace' },
  ],
}),
```

```scss
@use '@angular/material' as mat;
@use '@impulseframework/resource-angular/theme';
@use '@impulseframework/resource-angular/palettes';

html {
  color-scheme: light;

@include theme.palettes(
```

## Core Concepts

The central concept of the library is the `resourceConfig`. This configuration object defines the structure and behavior of a page or a part of a page. It specifies which components to render, how they are connected, and how they interact with data.

The `compound-component` component is the engine that brings the `resourceConfig` to life. It dynamically creates and configures components based on the provided configuration, allowing for highly flexible and data-driven UIs.

A row page is a compound page over one row, and the page owns that row. Its store reads the row once, by the key the page resolved, and every related config the page draws (an array view, a child list, a resolver's component, the RPC buttons) exists only once the row is present: no child asks for anything from a row that has not arrived, so an array view's `listFilter` is never written against an empty row and a child list never asks for an unfiltered first page. The page's own view provides no store of its own and draws and writes through the page's store, so a save in the form is what every other child of the page reads. A reload of the row keeps the row, the form, and the children on screen while the read is in flight. A row that could not be read is said in the page's own words in place of its form, never as an empty record: "This record is not here. It may have been removed, or it may no longer be yours to see." where the server found no row for the key, "You do not have permission to see this record." where the server refused the read as not permitted, and "This record could not be loaded." where the read failed. Nothing of the server's answer is on the screen, since it names ids, a permission and a resource, a database, or the search that found nothing; the view writes it to the browser's console, once, after the resource's name, for whoever looks into it. A `impulse-resource-view` therefore sits inside a compound page, where it shares the page's store, or on an element carrying `impulseRowStore`, which provides one for a view over a different row (the compound page places it on its related-row views); a view with no store in scope fails at construction naming `ResourceStore`.

A config describes the widest surface a page can have; the permission digest decides how much of it a given user gets. A create form renders only the inputs the digest grants for Create, and a list requests and renders only the configured columns the digest grants for List (key fields are structural and always pass), so one config serves a full-width role and a narrow one without a refusal in between. A create the form refuses (a required field left empty) is not sent: the form says so, beside its buttons on a page and under its fields in a dialog, and brings the first field it refuses into view, with its label, in whatever scrolls around the form. A field that is not shown (`shouldRender`, or a value the page gives it) keeps its place in the form and can be refused, the first one among them: the field brought into view is then the first refused one that is drawn, and since nothing on the screen can be marked for a field that is not there, the form's sentence names it by its label and says it is not on this form ("Call sign is missing or wrong, and it is not on this form."). Where no refused field is drawn, that is all the form says. Each field is drawn in an element that carries its name (`data-field`), which is how the form tells a field that is on it from one that is not. A row's form says the same sentence about a save it does not send. It refuses the changed fields that fail its rules, and a changed field can be off the form: one that another field's value takes off the screen and empties (`shouldRender` as a function, with `nullIfConditionallyHidden`) is changed by that and refused where the form requires it, so the sentence names it by its label ("Relay is missing or wrong, and it is not on this form."). A field the person did not change is never named: the save leaves it as it was. The sentence follows the form while the refusal stands: it is read again after each change of the form, so it stops naming a field that came back to the form and names one that left it since, and it goes once the changed fields pass. When the digest leaves a list no column at all, or the server refuses a request, the table says so in place of "No records found", in its own words: "You do not have permission to see this list." for a list the server refuses, "This list could not be loaded the way it was asked for. Try changing its filters or how it is sorted." for a filter, a sort or a page size it would not serve, "This list could not be loaded." for a request that failed. A column that names a related record (`additionalIds` naming a resource) is filled by a read of its own, by the keys the rows carry; when the server refuses that read, or it fails, the list is drawn all the same with the rows it has, each such cell saying what the page gives for a row whose record is not read (the column's `fallback`), and the list says above its rows what it could not read, by the column's heading and in its own words: "You do not have permission to see the records named in the Client column." where the server refused the read, "The records named in the Client column could not be loaded." where the read failed. Two reads that come to the same sentence say it once, and a sentence stands still while its read is asked again (a page turn, a sort or a filter brings other rows, so other records to read) and goes once that read answers. A read the server refused (an answer in the 400s) is not asked again for the same records while the list stays on the screen: a sort or a filter that brings rows naming the same records, in whatever order, makes no request, the sentence stays, and the console holds one line for it. A read that failed is asked again when the list brings its rows again, as the next answer may be another; so is a read the server had no time for (a 408, the request timed out, or a 429, too many requests), the two answers in the 400s that say nothing of the read itself. What the server said is never on the screen, here or in the empty table: it names ids, a permission and a resource, and the list writes it to the browser's console, once, for whoever looks into it. The same digest decides whether a row can be opened: a list draws its view arrow, and the row route admits, only when Read is granted, conditional or conditional on time for the resource, and a row whose read is refused says so in place of its form.

An enumerated field — one that holds another resource's identifier — lists exactly the resource the generated metadata names: `enumeratedResource` for a resource-backed picker (a field-scope `@enumerate` on the Go struct, or the schema's foreign key), or `enumeration` for a fixed value set the picker renders with no request. The field's `enumeratedConfig` narrows those rows (`filter`, `sorts`) and chooses their display; it cannot name another resource. The picker asks for the id and the display columns explicitly. A picker that displays several fields (`listDisplay`, `viewDisplay`) joins the ones a row has a value for, with a hyphen unless the config names another join: a person with a login and no name reads "marshal", never " - marshal". A picker with no display of its own shows each row's key. A field of the source that holds a role's name (`roles` in the source's metadata, from `@roleOf`) is shown in words, "Night shift lead" for `NightShiftLead`, which is what the server's sentences call the role, whether it is the key or a display field; the key is what the picker stores. A `searchable` picker over a source read whole narrows the loaded options as the user types, every typed word found in the display text, the id (so an identifier can be pasted), or one of the source's search fields, folded the way the server folds them; a `searchable` picker over a paged source narrows on the server, one page at a time, by the search box when the source has search fields the caller may list, else by a prefix match on the display field when its metadata lists `startswith`, with the box inside the panel and the page's count as the matches, and a paged source with neither is refused when the field is built, naming the resource and the DDL way out. Which fields a box searches is the source resource's, never the picker's: a picker that should search fewer fields lists a view projecting fewer token columns.

How a picker reads that resource is the descriptor's statement alone: its declared maximum page size (`@page max`). No maximum, and the picker reads the source whole in one request (`limit=all`) and resolves the chosen value from that list — an id the list does not hold shows as itself — so a source with no read route (a computed catalog, a key-less view) serves it. A maximum, and the picker pages the source one server page at a time at the descriptor's default size, with Previous and Next inside the panel following the server's cursors and the first page's total, sorted by the configured `sorts`, else the source's `@order`, else the display column; the chosen value is read by key and shown ahead of the page's options whichever page is open, and a source with a maximum serves that read (the generator refuses one that does not). A bounded source the server refuses (no order and no sort) says under the field that its list could not be loaded, never an empty list. A picker offers only what the person may see of its source, in every application, and what it says about that is the library's own sentence, never the server's answer, which names ids, a permission and a resource. The picker asks the permission digest before it asks the server. A source is closed to the person where the digest grants nothing of what the picker asks of it: List on a source read whole, whose list is all the picker asks; on a paged source, List while the field is edited, and both List and Read while it is read. A closed source is sent no request: the field is read-only, shows the stored id, and says under it "You do not have access to this list, so only the id is shown." (with nothing stored, while it is edited, "You do not have access to this list, so nothing can be chosen here."), and saving the form leaves the stored id as it is. Where the digest is not at hand, the server's refusal of the list as not permitted leads to the same state, and nothing more is asked. Where the source is open and the row the field holds is not the person's to read (the digest grants List and no Read, or the server refuses the read of that row, as a condition on the row does), the field shows the stored id and says "You do not have access to this record, so only its id is shown.", the row is not asked for again, and while the field is edited the picker stays a picker, so a row the person may read can be chosen; left alone, the field keeps the stored id. A source the generated API does not describe has no word in the digest and is asked. A request that fails for any other reason says so under the field in the library's words, and nothing is thrown at the page: for the list the picker offers, "This list could not be loaded, so only the id is shown." where the form is read and shows the id the field holds, and "This list could not be loaded, so nothing can be chosen here." where the field is edited, since the picker is drawn there with nothing to choose from, or holds nothing; and "This record could not be loaded, so only its id is shown." for the read of the row the field holds. What the server said of a request it refused or that failed, a refusal of permission included, is never on the screen: the picker writes it to the browser's console, once, after the resource's name and which of its two reads it was. The same switch decides how a list's referenced-resource columns resolve their display values (an unbounded source read whole once and mapped; a bounded one asked for one `filter=id:in:(…)` page per grid page over the page's keys, served by the key's index) and how an array view lists its children (whole, or one server page with Previous and Next). Nothing in the library reads every row of a bounded resource: the maximum was declared to keep the whole set out of memory, and declaring it is the author's deliberate switch.

A list page can list a view and write to the view's table. The view declares its backing table, a create goes into the table, and the new row shows up in the view on the next list because the view's SQL reads that table: the generated metadata carries the table as `rowsOf`, and the `listViewConfig` names the view alone as `primaryResource`. Rows, columns, `filter`, `sorts`, `parentRelation`, and the List-grant narrowing come from the view, since that is the resource the server enforces; create, edit, and delete go to `rowsOf`, the `elements` form is built for it, and the row page reads it. The list always requests the view's primary-key columns, read from the metadata, so an operation lifts the key the row carries — an association view keyed like its table is deleted from the list. `rowRoute` names a field of the view: a row opens that field's `enumeratedResource` on its page (the one `resourceRoutes` registered for it, else its metadata route) by the row's value in the field, and the View column is drawn when the caller may Read the target. Without `rowRoute` a row opens the write resource by its single key, and a compound-key resource with no `rowRoute` draws no View column. A `rowRoute` naming a field with no resource in the metadata throws when the page is built, naming the field. The list configuration cannot name another resource: `overrideResource` and `viewResource` are gone, and a config setting either fails to type-check.

A list pages on the server, and only there. The list component holds one page of rows — the resource's declared default page size (`@page`), or the config's `pageSize` — and the grid renders it and emits intents: a header click is the next sort, a filter menu is the next column filter, and the pager's First, Previous, and Next follow the cursors the server issued, with the total the first page answered kept while turning. Sorts and filters travel as request parameters, so the server orders and narrows every row it holds, not the ones the browser happens to have; a change to either asks for a first page again. The grid offers the server's filter grammar and no other: the ten comparisons on a column the generated metadata marks `filterable` — an indexed column always, an `allow_filter` column only once an indexed filter is in the request, since the server accepts it only beside one — and "Starts with", "Ends with" and "Contains" on a column whose field's metadata lists the match (`FieldMeta.search`), which stand alone, so a filter the grid offers is one the server answers. A column's `filterable: false` in the config removes a control the metadata would draw. The menu edits a draft: Apply, Enter in its value, or closing the menu commits it, and a new operator alone sends nothing, so an operator and a value changed together are one request, and a null test chosen alone commits as the menu closes. On a window narrower than the menu's controls side by side, a control that does not fit goes onto the next line at its own width, Apply and Clear together, so none is squeezed or cut at the menu's edge. A `civildate` column's menu takes its value from a date control, and a `date` column's (a timestamp) from a date control and an optional time of day, sent as `2026-12-15` or `2026-12-15T09:30`, which the server reads as the whole of that day or minute in the person's zone, sent on every request as the `Time-Zone` header by the resource client (the `@impulseframework/resource` README, Time zone header), so a list filters by the day the grid shows; "One of" and "None of" on those columns take typed dates, comma-separated, in the forms the server reads (`2026-12-15`, `12/15/2026`, `2026-12`, `2026`). A column whose field takes one of a fixed set of values (an `enumeration` in the generated metadata) takes its value from the names of those values, the names its cells write: one to pick under a comparison, each to tick under "One of" and "None of", offered in the metadata's order, which is the order a sort by the column puts the rows in. The filter carries the stored values, so the server is asked by key for what the person chose by name; a text match on such a column is typed, since it matches the stored value. A column over a key into another resource's rows (`enumeratedResource`) takes a typed key. A list over a resource with search fields (`ResourceMeta.searchFields`) draws the search box above the table unless the config's `showSearchBox` is false: its placeholder names the fields it searches for this caller (the resource's, less those the digest denies for List; a child's field, listed under the child's name, judged by the child field's grant on the child resource through `ResourceMeta.searchBranches`), the hint under it names the fields the role leaves out, typing commits after a pause and is sent as the filter's `*:search:"…"` conjunct, the title's count becomes the matches, a companion column lights up while the box is active, and clearing the box restores the unnarrowed page. Which fields the box searches is the resource's and the caller's grants, never the page's. The request travels in the body, as the server requires, exactly when the page's filter, a column filter or the box reaches a field the metadata marks `pii` (`FieldMeta.pii`, a branch's `pii`); `disableCacheForFilterPii` forces the body for a filter the metadata cannot read. Selection is held as rows and spans pages. `ListViewConfig.limit` is gone: a list never gathers every row for the browser to slice, and the row-count title reads the server's total.

A list page can list a resource across tenants. A tenant-scoped resource declared for it (`@listAcrossTenants`; its generated descriptor says `acrossTenants`) is listed by a page outside every tenant with `acrossTenants: true` on its `listViewConfig`: one request, without the tenant's segment, for the resource's rows in every tenant the person reaches in which they may list it, with the page's one filter, sort, page and count across them. It is the table's second column: the page's first column, the one that names the row, stays first and is the one column the table holds in place while the rest scroll sideways, and the tenant scrolls with the rest. The page is bound to no tenant: selecting another in the place switcher asks for nothing again. It reads: it draws no create button, no delete and no method, whatever its config names, because every write stays inside one tenant, on the row's page; `enableRowExpansion` is refused when the page is built, naming the resource, as is `acrossTenants` over a resource the descriptor does not say is listed across tenants. A column that reads a referenced tenant-scoped resource (`additionalIds` naming one) shows nothing, since the page has no one tenant to read it in; the tenant column's header is words with nothing to press and keeps no room for a sort arrow, the tenant not being a field of the resource, and a page that wants its rows grouped sorts by the resource's own tenant field where it lists one. Narrowing the list to some of the tenants is the client's (`client.acrossTenants.<resources>.page({ domains })`, the `@impulseframework/resource` README); the page lists every tenant the person reaches.

A list says what it has to say in the page's own words, and a row can carry a button for what is no method. `emptyMessage` on the `listViewConfig` is what the empty table says where the list holds no row at all ("This application declares no feature flags.") in place of "No records found"; a list narrowed by a filter or the search box that leaves no row says the plain text, and a refusal, a failed request and a list with no column the person may see keep the list's own words for them, never the server's. `rowButtons` names the buttons every row carries ahead of its menu of methods (`{ label, icon, run: (row, injector) => … }`), for what a person only reads and the server serves as no method, opened in a pop-up (a flag's history): an icon button named by its label, handed the row as the server answered it and the list's injector. The grid draws its headers as buttons that ask for the next sort; a table whose rows come in the one order they have (a history, newest first) passes `[sortable]="false"`, and its headers are words with nothing to press. A list over a computed resource (the generated metadata says `computed: true`) is ordered, filtered and searched by the server over its real values, so the server answers by a field only where the person's grant on it has no condition left once the request is checked. The digest says which fields those are: one it lists as `granted`, or as `conditionalOnTime` (held at certain times, which the server settles at each request), is answered, and one it lists as `conditional` (judged by more than the time: row by row, or by a fact about the person) is refused. So the list draws the heading of a `conditional` column as words and no filter control on it, a picker over a paged computed resource does not narrow by such a field as the person types, and the list draws no search box while a searched field is `conditional` or not listed, and says why where the box would be: "You cannot search this list: your role does not always see Mission.", "You cannot search this list: your role does not see Name." A grant held at certain times is offered at all times: outside them the server refuses the request as it refuses one for a field the person does not hold.

A list's create opens in a dialog. A column keeps a readable width and is no wider than what it holds needs, and a list whose columns do not fit scrolls sideways inside its own frame. The narrowest a column of text goes is what its heading, with the sort and filter marks beside it, and the longest value the list is showing need, with the cell's padding, and never more than 160 pixels (`MIN_TEXT_COLUMN_WIDTH`: 135 pixels of text at the list's 14 pixel type, about nineteen characters, which is a person's first and last name). It reads how wide its frame is in the same pass, before what it has drawn is shown, so a list drawn with its rows from the start (a list in a dialog) is shown once, at the widths it keeps. An icon is read by its box, whatever is drawn in it: where the icons' font has not arrived, an icon is laid out as the letters of its name, which run past the box that clips them, and a column of icons is as wide as the icon needs and never as the word. A column that draws its list a line each (`lines`) is read by its longest line. Each read is brought back to what the page lays out: a browser hands back what it draws, and a list inside something drawn smaller for a moment, a dialog that grows open at about nine tenths of its size, would be read as needing that much less and cut its widest value once the dialog had opened. A list that is loading is read for its widths once it has loaded. A list that has never been read is not drawn while it loads: its frame keeps its place and its room with nothing in it, neither headings at a width they would then leave, nor a pager that knows no count, nor a loading cover, which belongs to something a person asked for and not to a page's own first load; the page around it is there, and once the rows have arrived the list is read and drawn whole, an empty list and one that could not be read with the sentence that says so. A row is drawn once what its columns show is known: a column that names a related record (`additionalIds`) waits for the read of those records, so a row never shows the record's key first and its name after, when the list opens or when a row arrives later, and the rows the list already drew stay as they are until the new ones can be drawn with them. A row is drawn with everything it is drawn from, so a page across tenants is the list's only once the digests its rows' links are drawn from have been read. A list a person has seen keeps what it shows while it is read again, for a page turn, a sort, a filter or a refresh, under the loading cover. What a column needs grows when a longer value arrives and does not come down while the list stays on the screen with the same columns, so a column drawn at what it needs does not narrow as a person pages, sorts or filters; it starts again when the columns change or the list is opened again. Nothing is read while a font the page asked for is on its way, since the letters drawn in its place have another width. A list that has not been read yet is not drawn while it waits, so no column is seen at one width and then at a narrower one: its frame and its pager keep their place and their room, with nothing drawn in them, the page around it is there, and once the font has arrived the list is read and drawn whole. It is held back from when it first finds the font on its way, loading or not, and it stays held back until it is read, which for a list still loading is when it has loaded. The wait ends three seconds after a list of the page first found a font on its way, which is as long as a browser itself waits before it draws other letters in a font's place; a font that never arrives holds the first list of a page back that once, and no list after it. From then the list is read in the letters the screen shows, and a font that arrives later is read as a longer value is, growing a column and narrowing none. A list a person has already seen is never taken off the screen for a font: it keeps its widths, and is read again once the font has arrived. A list handed other columns has not been read with them, and waits as a new list does. A column that declares a `width` keeps that width, a column a person dragged keeps the width they gave it, and the select, expand and button columns keep theirs. A frame wider than the columns at their narrowest has room left over, and that room goes first to the columns that cut a value: each is given what it lacks to show its values whole, and while the room does not reach for all of them they share it equally, the least cut made whole first, with every other column at what it needs. For this the list reads what a column's values need past 160 as well, as far as the width of its frame, which is the most a column is ever given. A value that needs all of its frame is read no further, and the list reads its columns again when the frame grows wider than that one, so a list first drawn on a phone held upright cuts no more in a wide window than a list first drawn there. Once every value is whole the list does as it always has: the table fills the frame, a column that needs more than an equal share of it keeps what it needs, and the others share the rest, so a column that grows there takes its room from those that share, never below what they need. Where the frame is narrower than the columns at their narrowest, the table stays as wide as they need and the frame scrolls left and right, as it scrolls up and down; the page around the list does not scroll sideways. The first column then stays at the left edge, with the select and expand columns where the list has them, so a person always sees which row they are on while the other columns scroll under it; it is the one column held, never two, and a row's button columns scroll with the rest. The list holds it only while the widest of the columns that scroll can be seen whole beside the held part, so every column can be read in full beside the first, each in its turn; with less room than that nothing is held and every column scrolls. A list has 336 pixels on a phone 390 wide, where a first column and a widest other column of 160 each are held (320), and 306 on one 360 wide, where they are not. Rows stay one line, the header stays at the top of the frame, a control the keyboard's focus lands on is brought into view beside the held column, and the empty list's message and an expanded row's detail stay as wide as the frame and in view. A held cell is drawn on the color the list sits on, which the grid reads off the page around it, under the same tints as the rest of its row, so nothing scrolls through it in a light or a dark look and the list needs no background of its own. None of it is configured: a column's `width` is the one thing a page sets.

The pager under a list says which rows the page spans and offers First, Previous and Next. They share one line while the list's frame holds them; in a frame too narrow for both, a phone's, the buttons go under the words, at the far end, so none of them is cut off by the list's edge.

Printed, a list is as long as its rows. Nothing of it scrolls or is cut off, the pager comes after the last row, and the browser repeats the heading row on every page the rows run onto. A heading is not pressed on paper, so its button is drawn as its words alone, which is what lets a browser draw them again on each page.

A list offers the methods that run against its rows, with nothing configured. A part of the key the metadata lists in `target.mayBeEmpty` (a text field the method does not declare required, such as the group of a role a person holds directly) is sent as the empty text where the row holds it; a row that is empty in any other part of its key names no row, and its action is refused before a dialog opens. An entry runs the method through `MethodDialogComponent`, drawn from the metadata alone: the request fields that carry the row's key are filled from the row, every other field is an input by its display type (a picker where the field declares one, a picker of several for `enumerated[]`), required where the method requires it, and a method that takes nothing more than the row is a question with a button. A method that takes files (`@upload`) has a file input beside its fields: nothing is sent until a file is chosen, the request and the files travel together as the method's handle sends them (`upload(body, files)`), the input says the method's declared maximum, and how many files the method takes is the method's to refuse, in the dialog like any refusal. Where the caller's grant on the method carries a condition that may read the request, the dialog rehearses the call as the person fills it. The digest says the grant is `conditional` and cannot say for which values; the generated metadata names the request fields a condition may read (`attribute`, from `@attribute` on the Go field) and says which methods a dry run previews (`dryRun: true`, a method that runs in a transaction). The values a picker offers are not each tried: the picked one is. A method no condition can judge by its request (its grant's condition reads the row, which the row's own Execute answer already judged), one that runs outside a transaction, and one that takes files are not rehearsed. On a row of any other resource it is offered as any other filled method is, by the grant alone. The row page offers its row's methods the same way: where a method runs against a row of the page's resource, the read of the row asks for the Execute answer beside Update and Delete, and the page draws one Actions menu holding the methods the answer lists, presented by the same `rowMethods` (a page with a list shares it with its row page; `rowMethods: false` asks nothing and draws none). A domain-scoped resource's metadata route carries the tenant parameter in braces, so such a page sets `routeData.route` to the path it lives at. That route may carry the tenant parameter as the router names it (`sectors/:sectorID/missions`: the API's domain route segment, the descriptor's `domainRoute.param` after a colon, then the page), mirroring the API's URL, and the links the page builds from it follow the page's tenant: the View column, the table button, the after-create navigation, and the page another list's rows open on put the tenant in the parameter's place, read from the route's parameter when the page is under it and from `RESOURCE_DOMAIN` otherwise, so a row link is the row's real URL and opens in a new tab. A route naming no parameter is used as written. The resolver is `pageRouteResolver()` from `@impulseframework/resource-angular/resource-nav`, for an application's own links from a registered route; it refuses a route naming the parameter when no tenant is known, naming the route.

A list page or a record page can be live: it stays current without polling and without refetching while nothing changed, and a page left and opened again inside five minutes is served by the browser with no request. A page is live by default when the generated metadata says its resource's changes are published (`ResourceMeta.live`, true on every table-backed resource); `live: false` on its `listViewConfig` or `viewConfig` opts it out, `live: true` on a resource whose metadata says its changes are not published (a view or a computed resource) is announced once and asks plainly, and metadata from a generator that predates the field makes no page live by itself (the list page's row page follows the list's config). Provide the change feed once in the application's providers: `{ provide: CHANGE_FEED, useFactory: () => firestoreChangeFeed() }` from [`@impulseframework/resource-firestore`](../resource-firestore/README.md). `AuthService` starts the client's live session with the feed when the session first authenticates, fetching the feed's identity from the API, and stops it at logout, before the session is logged out, so every subscription of the user is deleted and the feed's identity revoked first. From then on the store's list page carries the client's live option (the tab subscribes to the resource in the selected tenant, and a change requests the page again by its own cursor, with the change's version) and the row page carries it for its row (a change reads the row again, the form and the children staying on screen while the read is in flight); a resync reads both again by a fresh seed, and a tenant change moves the list's subscription. The client's live session says when: a write the person made in this tab shows at once, when the write is answered, and the feed's report of the same write requests nothing; other people's changes wait two seconds from the first and become one request, at most one every five seconds while they keep coming; and a tab that is not shown requests nothing until it is shown again, then once. A component's own reload after its own write (`reloadPage`, `reloadViewData`) is the request the session already made, not a second one. An application sets the two times where it creates its client: `provideResourceClient((options) => createApi({ baseUrl: environment.apiUrl, ...options, live: { ...options.live, changeWait: 1_000, refetchInterval: 10_000 } }))`. The page's other readers (pickers, referenced-resource lookups, array views, create forms) never ask to be live. Without a provided feed, or on an outlet that serves no live subscriptions, a page configured live asks as a plain one: nothing is cached, nothing is subscribed. What the option opts into, what it costs, and what it never does are in the client's README under "Live pages".

A feature can ship dark and be turned on per environment, and the pages follow the switch. For a feature with a resource behind it there is nothing to add: while its flag is off the server leaves the resource out of the permission digest, so the menu item, the buttons, and the row page are hidden by the digest alone, and `resourceRoutes` adds a match guard from the metadata's `feature`, so a dark URL falls to the application's wildcard route as any unknown URL does. For a feature with no resource behind it the library offers three gates, each taking a member of the generated `Feature` union so a misspelled flag fails to compile: `*impulseFeature="Feature.Debriefs"` on an element, beside `*impulseHasPermission`, renders it while the flag is on; `featureMatch(Feature.Debriefs)` in a route's `canMatch` matches the route only while the flag is on; and `feature` on a page or an action of the menu file (below, under the frame) beside `permission` leaves the entry out of the menus while it is off. A group, a submenu or a menu whose every entry is left out, by a flag or by the caller's permissions, is left out too, so nobody is shown a heading that opens on nothing. `AuthService` loads the enabled set once when the session first authenticates, beside the digest and the domains, and forgets it at logout; `featureEnabled(name)` answers from it, signal-backed, and `ensureFeature(name)` loads it first for a guard that may run before the session's first check. On an API that serves no feature flags (a descriptor without the `features` route, from a generator that predates them) `AuthService` skips the load and every gate answers off: `*impulseFeature` renders nothing, a `featureMatch` route falls to the wildcard, the first ask of each flag is announced once through the client's `warn` option (the console by default), naming the regeneration that would serve it. Nothing polls and nothing is pushed: a flip by someone else is seen at the next sign-in, by design.

**The Feature flags page** is the library's (`@impulseframework/resource-angular/feature-flags`), and every application places it: `featureFlagsPage(resourceMeta)` in the menu file and `featureFlagsRoute(resourceMeta)` among the routes of the place outside every tenant (an untenanted application's own routes). It is the library's list over the feature flags resource and draws nothing of its own: each declared flag by its name in words (`cargo_manifest` is "Cargo manifest"), its description, whether it is on, and when and by whom it was last turned on or off ("Never" for a flag nobody has flipped; the two are read from the flag's history, and their headers offer no sort). It is shown under List on the flags. A row's Actions menu holds Turn on for a flag that is off and Turn off for one that is on, for a person the digest grants the generated `SetFeature` method; the person is asked first ("Turn Cargo manifest on for everyone in this environment?"), a refusal is shown in the server's words, and once the flip is written the client reloads the enabled set and the digest, so the person flipping sees their own pages follow at once. A person who may list the flags and not flip them sees the list without the menu. Each row carries a History button, which opens the flag's flips in a pop-up, newest first: when, what it was turned to, and by whom (`client.features.changes(name)`, the flag's `changes` route, which whoever may list the flags may read; a column the person's role shows nothing of, as the role shows nothing of the same fact in the list, is not drawn). The pop-up is its own entry point (`@impulseframework/resource-angular/feature-flag-history`, `openFeatureFlagHistory(dialog, { name, words })`), loaded when a person first asks for a history, so the page costs the first paint nothing. An application that declares no flag reads that it declares none.

An application installed as a progressive web app can tell the person when a new build is ready and reload only when they choose. A progressive web app is one the browser can install, with a service worker: a script the browser runs apart from the page, which keeps the application's files and downloads a new build when one is deployed. The library provides this through a secondary entry point, `@impulseframework/resource-angular/ui-app-update` (an import path of its own beside the main package), which exports `provideAppUpdate()`. The application adds `provideAppUpdate()` to its providers beside Angular's `provideServiceWorker(...)` and nothing more: no component references the service, and the notices it raises render in the alert area every application already has, the `impulse-alert` list over `NotificationService.notifications()`. `provideAppUpdate()` starts `AppUpdateService`, which listens to `SwUpdate`, Angular's service for the worker's events, from `@angular/service-worker`; that package is an optional peer dependency of this library: an application installs it when it uses this entry point. The service is inert when no service worker is provided or the worker is disabled, as it is in dev mode and in component specs: no timer starts and nothing is raised. When the worker reports that a new version is ready (`VERSION_READY`), the service raises one persistent notice, "A new version of this application is ready.", with a Reload action; it never reloads on its own, and the person chooses when. When the worker reports a state it cannot recover from (`SwUpdate.unrecoverable`), the service raises the same kind of notice, "This application needs to be reloaded to keep working.", with Reload. Checks for a new version run hourly while the browser tab is visible and once whenever the tab becomes visible again, and none run while the tab is hidden, so a hidden tab never wakes a server instance for nothing; the worker itself also checks after every page load. The hourly timer runs outside Angular's zone, the layer that tracks pending timers and requests and reports the application stable, or settled, once none is left, so it never keeps the application from settling. Every reload goes through one injectable class, `AppReloader`, whose `reload()` calls `location.reload()`, and a spec provides its own in its place to observe a reload. The service also exposes four members other parts of the library use: `ready`, a signal that is true once a new version is ready; `checkNow()`, which asks the worker to check and resolves true when a new version is ready; `reload()`; and `reloadWhenReady()`, which reloads onto the new version with no notice as soon as the worker has one ready, at once when one already is. To carry the Reload action, `CreateNotificationMessage` and `NotificationMessage` (in `@impulseframework/resource-angular/types`) gained two optional fields: `action`, a `NotificationAction` with a `label` and a `run` callback, which `AlertComponent` renders as a button beside its close; and `persistent`, which makes the alert skip its auto-dismiss timer so the notice stays until it is closed or dismissed by its id. A notice that sets neither renders and expires exactly as before. A related fix in `IdleService` (`@impulseframework/resource-angular/auth-idle-service`) moved its keep-alive, the periodic session check, so it now starts in `start()` and ends in `stop()`, as the idle ticker (the timer that watches for inactivity) already did, where before it started in the constructor and never stopped. A signed-out application therefore has no timer due and can settle, which is what lets the service worker register as soon as the application is stable. No request behavior changes: the keep-alive already sent nothing without a session.

The application reloads by itself in one case: when the server refuses this build's release, `AppUpdateService` picks up the server's build. While the application is still starting, meaning its router has not yet completed a navigation (`Router.navigated` is false, so no page is on screen yet), the service calls `reloadWhenReady()`: the worker is asked for the new build, and the document reloads onto it as soon as it is ready, with no notice. When there is no service worker, or no new build is ready within ten seconds (`RELOAD_WAIT_LIMIT`), it does an ordinary reload. Once a page is on screen, the service reloads nothing by itself and raises one persistent notice, "A new version of this application is required. Reload to continue." (`OUT_OF_DATE_MESSAGE`), with Reload. A tab reloads by itself at most once per server release: the guard is the server's release, which the service keeps in `sessionStorage` (the browser's storage for one tab, which survives a reload) under `impulse.app-update.reloaded-for` (`RELOAD_GUARD_KEY`), with every read and write wrapped in try/catch, and a refusal past the guard, one for a release the tab has already reloaded for, raises the notice instead of reloading. When the server runs an older release than this build, as after a rollback, the client has already retried the request, and a plain reload would not help, since the worker would serve this newer build again; so the service unregisters every service worker (`AppReloader.unregisterWorkers()`) and then reloads onto the server's build, whether or not a page is on screen. Past the guard it raises "The server runs an older version of this application. Reload to continue." (`SERVER_OLDER_MESSAGE`), whose Reload does the same.

The application tells the person when the server is down for maintenance and takes the notice down by itself when the server is back. The deploy pipeline starts a release that interrupts the database behind a maintenance revision of the application, which answers every request with status 503 and the marker header `X-Maintenance: 1`; the client throws such an answer as `MaintenanceError`, and the client's README says how it tells it from an ordinary 503. The client's error hook hands it to `MaintenanceService`, a service of the same entry point beside `AppUpdateService`, through the `MAINTENANCE_HANDLER` token, which `provideAppUpdate()` provides too. The first answer of an outage raises one persistent notice, "This application is down for maintenance. It comes back by itself when the work is done." (`MAINTENANCE_MESSAGE`), with no action, since there is nothing the person can do; it is the library's sentence, never the server's text or status; and the answers that follow while the notice is up change nothing, so an outage raises one notice, not one per failed request. While the notice is up the service checks back: the first check after the server's `Retry-After` (`MaintenanceError.retryAfter`), or fifteen seconds (`MAINTENANCE_CHECK_START`) when the server named none, and each check that finds the server still down doubles the wait up to two minutes (`MAINTENANCE_CHECK_CAP`); no check runs while the tab is hidden, one runs as soon as it is visible again, and the timer runs outside Angular's zone as the update service's does. The check is `MaintenanceProbe.stillDown()`: one HEAD request for the application's own entry document under its base href (`document.baseURI`), the request the maintenance page's own check-back makes. It needs no session and no database and carries no body either way: a maintenance server answers it 503 with the marker, since it is not a navigation, and the application's server answers it with the document's headers. It is sent past the service worker with the `ngsw-bypass` header (`WORKER_BYPASS_HEADER`), which Angular's worker honors, so the worker never answers it from its cache of the application's files, and past the browser's cache (`cache: 'no-store'`); a request that gets no answer at all counts as still down, since the server is between revisions. The first answer without the marker, whatever its status, is the recovery: the notice is dismissed, the checks end, and the service calls `AppUpdateService.checkNow()`, so a new build installed meanwhile raises the update notice, and the next request of the client is answered, or refused under the release rule above, which does the rest. `MaintenanceService.down` is a signal that is true from the first answer of an outage until the recovery, and a spec provides its own `MaintenanceProbe` to script an outage.

Every application provides its generated client: `provideResourceClient((options) => createApi({ baseUrl: environment.apiUrl, ...options }))` in the application's providers, with `API_URL`, `BASE_URL`, and `API_VERSION` beside it. `API_VERSION` is the release this build was made from, as the build stamps it (into an environment file, for example), and is empty or `dev` for a local build; `provideResourceClient` hands it to the client as `ClientOptions.apiVersion`, so every request of the client carries it in the `X-Api-Version` header. `provideResourceClient` also hands the client's live session the XSRF token Angular's extractor reads from the cookie `withXsrfConfiguration` names, so the page-leave unsubscribe, which rides a keepalive fetch rather than HttpClient, echoes the application's cookie and the cookie is named once. The library's store, pickers, guards, and `AuthService` all speak through that client, and an application that provides none fails at startup naming this call as the way in. The client is the one place a response becomes an error, and the adapter renders its judgment five ways. A 401 is the session gone: the client's error hook keeps the attempted URL in `AuthService.redirectUrl` and returns the browser to `FRONTEND_LOGIN_PATH`, where the login page reads the URL once the session is back (on the login page or the sign-out page already, nothing moves and nothing is kept). An `ApiError` nobody caught raises one global error notice in the server's words (the body's `message`, else `HTTP <status>`), through the `ErrorHandler` the same call provides, and a request that got no response at all raises one saying so; a refusal a page reports in place raises nothing, since handling the error is what silences the notice: the store's `pageError`, the row page's `viewError`, a component's own refusal signal, and a method's declared answer (`@answers`) all render where they happen and reach no notice. A 412 carrying the server's release is the server's refusal of this build, `ApiVersionError`: the client's error hook hands it to the update service through the `VERSION_REFUSAL_HANDLER` token, which `provideAppUpdate()` provides, and `ResourceErrorHandler` raises no notice for it, since the update service reloads or raises its own. A build that names a release without `provideAppUpdate()` fails at startup naming `provideAppUpdate()`. A 503 carrying the maintenance marker is the server down for maintenance, `MaintenanceError`: the hook hands it to the maintenance service through the `MAINTENANCE_HANDLER` token, which `provideAppUpdate()` provides too, and `ResourceErrorHandler` raises no notice for it, since the maintenance service raises its own; without `provideAppUpdate()` the answer goes to nobody and raises no notice, and a 503 without the marker is an ordinary error and raises the notice in the server's words. The library does not recognize the refusal, or the maintenance answer, of a hand-written `HttpClient` call: `apiVersionInterceptor`, below, adds the header to such a call, the application's own error path sees the 412 or the 503, and the next request of the client triggers the update service or the maintenance service. Every request the client sends begins and ends `UiCoreService` activity, so `isLoading` and the progress bar move while any request is open. The library ships one functional `HttpClient` interceptor, a function `HttpClient` runs over each request it sends: `apiVersionInterceptor` (exported from `@impulseframework/resource-angular/resource-client`), which adds the same header to the application's own same-origin `HttpClient` requests (those sent to the application's own scheme, host, and port), a login form's POST, for example. The application registers it as `provideHttpClient(withInterceptors([apiVersionInterceptor]), withXsrfConfiguration({ ... }))`. It adds nothing for a build that names no release or `dev`, leaves a request to another origin alone, and keeps a header already on the request. `HttpClient` still keeps the XSRF cookie echo (`withXsrfConfiguration`). A provider placed after `provideResourceClient` that re-provides `ErrorHandler` would silence the notice, so startup fails naming the way out when the handler in effect is not the library's: `importProvidersFrom(BrowserModule)`, which `BrowserAnimationsModule` carries, does this, and `provideAnimationsAsync()` is its replacement; an application's own handler extends `ResourceErrorHandler`. Hand-written `HttpClient` traffic outside the client is the application's to render.

An application that signs people out when they stop using it starts `IdleService` (`@impulseframework/resource-angular/auth-idle-service`) once, after sign-in, and stops it at sign-out; the skeletons do this in their root and login components. The service counts the seconds since the last activity (a mouse movement, a key, a click, a scroll, a touch) and, for the last `IDLE_WARNING_DURATION` seconds of the `IDLE_SESSION_DURATION` (sixty of three hundred by default), shows one persistent notice in the alert area, "You will be logged out in N seconds due to inactivity.", counted down in place; persistent so the alert's own thirty-second auto-dismiss never hides it before the sign-out. Any activity ends the warning on the next tick, the notice's close button among them, since a click is activity: the application knows the person is back and asks for nothing more. At the end of the session the service runs `IDLE_LOGOUT_ACTION`, stops, and sends the browser to the sign-out route (`FRONTEND_SIGN_OUT_PATH`), where the signed-out notice shows. Every `IDLE_KEEPALIVE_DURATION` seconds (thirty by default) it also asks the server for the session while one is signed in, so a session the server ended is noticed. `IDLE_TIMEOUT_REQUIRE_CONFIRMATION`, which once made the warning hold until the application's own stay-signed-in button called `stayLoggedIn()`, is retired and has no effect: a provider of it keeps compiling, `start()` logs once in the console that it does nothing, and `stayLoggedIn()` stays for an application that still offers a button.

A login page shows text it holds, never text from the URL. A refused OIDC login returns the browser to the login page as `<login page>?code=<code>`, and the code is all the session package sends; its "Login refusal codes" table is the finite list. `LOGIN_MESSAGES` holds one sentence for each of those codes (`DEFAULT_LOGIN_MESSAGES`), `UiCoreService.loginMessage(code)` answers the sentence or an empty string for a code the application does not know, and `publishLoginError(code)` raises it as a global error notification and says whether the code was known. The page reads the `code` query parameter and renders the lookup, so a crafted URL renders nothing. A refusal the server answers on a step of the sign-in itself (a password POST, a confirmation) carries its code in the body, whatever its status, and the page reads it from there: a 401 or 403 for the policy's refusals, and a 429 for the session library's attempt limiter, which refuses a name whose failed password attempts reached the limit with the code `too_many_attempts` and the wait before the next attempt, `retryAfter` in seconds (and the `Retry-After` header), and for its mail limit, which refuses a code or link to an address sent as many as it allows, none used, with `too_many_emails` and the same wait. A component that asks for mail keeps its button disabled for that wait with `MailHold` (from `@impulseframework/resource-angular/ui-core-service`). `loginMessage(code, retryAfter)` and `publishLoginError(code, retryAfter)` take that wait and follow the sentence with it, "Too many attempts. Try again in 14 minutes.": in minutes from a minute up, rounded up, and in seconds below it ("Try again in 45 seconds."); without a wait the sentence stands alone ("Too many attempts."). An application whose session data resolver refuses with a code of its own, or that wants a default reworded, adds `provideLoginMessages({ not_provisioned: 'Your account has not been set up yet.' })` to its providers: the library's sentences come first and the application's after, and a reworded `too_many_attempts` is followed by the wait the same way.

## Permission questions in reactive code

The client's permission answers (`api.can()`, a handle's `can()` and `grantedFields()`,
a method's `can()`), its feature flags and its session read plain stores, and
`provideResourceClient` makes every such read an Angular dependency (`trackStoreReads`).
A question asked inside `computed()`, `effect()` or a template is therefore asked again
when its store changes: a digest loading, a digest read again after a role changed, the
permissions cleared at sign-out. Nothing mirrors a store first;
`storeSignal(store)` remains for a signal to pass along.

A `resource()` loader is not reactive code: Angular runs it untracked, so a permission
answer read inside a loader is read once and never reloads the resource. Put the answer
in the resource's params, where it is tracked, and branch on it in the loader:

```ts
private canList = computed(() => this.api.domain(this.tenantID()).tenantDirectories.can(Permissions.List));

directories = resource({
  params: () => ({ tenant: this.tenantID(), listed: this.canList() }),
  loader: ({ params }) => (params.listed ? this.api.domain(params.tenant).tenantDirectories.list() : Promise.resolve([])),
  defaultValue: [],
});
```

`provideResourceTesting` tracks store reads the same way, so a spec that loads a digest
sees a computed answer follow it.

## The frame

The frame is what every signed-in page sits in: a bar across the top with the application's name, the place the page is in, the menus and the person's own menu, and on a phone a menu button that opens the same menus in a side panel. The application gives its name, its menu file and the name of the place outside every tenant; the library draws the rest (`@impulseframework/resource-angular/auth-frame`). There is no footer: the release is in the About pop-up.

Provide it after the client, and route every signed-in page as a child of `FrameComponent`:

```ts
// app.config.ts
provideFrame({ name: 'Lodestar', home: 'dashboard', outside: { label: 'Configuration', icon: 'settings' }, menus });

// app.routes.ts
{
  path: '',
  component: FrameComponent,
  canActivate: [LoginAuthenticationGuard],
  children: [
    { path: '', pathMatch: 'full', canActivate: [homeGuard], children: [] },
    refusedRoute(DomainRoutePath),
    { path: '', canActivate: [outsideGuard], children: [...outsidePages, ...frameRoutes()] },
    { path: DomainRoutePath, canActivate: [tenantGuard], children: [...tenantPages, ...frameRoutes()] },
    { path: '**', redirectTo: 'dashboard' },
  ],
}
```

The place outside every tenant comes before the tenant segment, and the one wildcard comes last, outside both. A list page over the tenant record lives at the record's own address, as the API has it (`tenants`, and a row at `tenants/acme`), which the segment would otherwise take for the tenant `acme`; every longer address under a tenant matches no page outside and passes on to the segment.

- `name` is drawn at the upper left as a link to the application's root; without it no name is drawn.
- `home` is the first page of every place, a path under the place. Signing in arrives at the root, where `homeGuard` sends the person to the first page of the place they land in.
- `outside` names the place outside every tenant, for the switcher and the menus. Without it the place is Configuration, with a gear.
- `menus` is the menu file: the menus across the top, in order. The function form, `() => Menu[]`, is called once in an injection context, so an action of the application's own may use a service it injects (`const dialog = inject(MatDialog)`, then `run: () => openNewTenantDialog(dialog)`).
- `help` and `person` are the application's own entries in the Help menu, above About, and in the person's menu, above Appearance.

`provideFrame` also provides `RESOURCE_DOMAIN` as the tenant the URL is open in, so every library page asks in it.

**What scrolls.** The frame is as high as the window, and the page scrolls inside it: the banner and the bar stay at the top, and the element under them (`.impulse-frame-scroll`, around the page's `main.impulse-frame-page`) scrolls up and down and sideways. The document never scrolls. So a row a page keeps at the top (`position: sticky; top: 0`, as a list's heading rows are where the application turns `--sticky-headers` on) stays right under the bar, the side panel is as high as the window however long the page is, and a pop-up opened from the page follows the page (the element is a `cdkScrollable`). A page that needs to know how far it is scrolled, or to scroll itself, asks that element and not the window. The keys that scroll a page (Page Down and Page Up, Space, the arrows, Home and End) scroll it as they scroll any page: a browser sends them to the document while nothing has the focus, so the first of them pressed then gives the focus to that element, which is no stop of the Tab key and shows no line around the page. Every element of the frame is named for the component that draws it: the frame's own are `impulse-frame-…`, the bar's `impulse-frame-bar-…`, the drawer's `impulse-menu-drawer-…`, the menus' across the top `impulse-menu-bar-…`, an opened menu's `impulse-menu-list-…`, the person's menu's `impulse-person-menu-…` and the place switcher's `impulse-place-switcher-…`. The pages the library draws inside the frame are named the same way: the account page's elements are `impulse-account-page-…`, the API keys page's `impulse-api-keys-page-…`, the directory groups page's `impulse-directory-groups-page-…`, those of the page a refused tenant gets `impulse-tenant-refused-…`, and the About pop-up's `impulse-about-dialog-…`. So a rule an application writes for its own content (`.main`, `.panel`, `.page-content`, `.row`, `.page`, `.menu`, `.bar`, `.brand`, `.name`, `.none`, `.message`, `.about`) never lands on the frame or on those pages. The room around the page is the frame's own: 16px above and below and 24px beside it, or what the application's stylesheet sets `--impulse-page-padding` to on `:root`. Printed, the frame is as long as the page.

**Pages and the menu file.** A page holds its own label, icon, address, and the permission and feature flag it needs: `page({ label: 'Customers', icon: 'apartment', route: ['customers'], permission: { resource: Resources.Customers, permission: ListPermission } })`. The route carries it, `pageRoute(customers, { path: 'customers', component: CustomersComponent })`, and the menu file places it by reference: `{ label: 'Records', groups: [{ entries: [customers] }] }`. The address says where the page lives. A route with a part naming the tenant parameter (`tenants/:tenantID/users`) is a tenant's page, shown while a tenant is open and filled with it. A route that starts with `here` is a page every place has, opened where the person is (the library's account page is such a page). Any other route is a page of the place outside every tenant, shown only there. So choosing a page in a menu never moves the person to another place. Beside pages, an entry is an action (`{ label, icon, run }`, with `place: 'outside'` to keep it to the place outside every tenant) or a submenu (`{ label, icon, groups }`). The menus leave out every entry the person may not use, by its permission (a list means any one of them) and its feature flag, and then every group, submenu and menu left empty. The answer follows the session: a tenant opened, a digest loaded, a flag flipped, and the menus redraw. The library appends Help, last on the bar, ending with About and the application's name: an action that opens the About pop-up over the page the person is on.

A config-driven page names its label and icon on its config, `page: { label: 'Missions', icon: 'rocket_launch' }`. `resourceRoutes` makes the page at the page's route, needing List on the resource and behind the resource's feature flag unless the config says otherwise, and carries it on the route; `resourcePage(config, resourceMeta)` answers the same page object for the menu file. A config without a page makes a page no menu reaches, such as one only a row link opens. The pages over an Auth's people do the same through `identityMenuPages`. A page that lists its resource across tenants (`acrossTenants`) is mounted at `routeData.route`, which it must name, with no row route. No one tenant's digest speaks for it, and the application names no permission for it: the page needs, and its route is guarded by, the global digest's answer that the person may list the resource in at least one tenant they reach (`ListAcrossTenantsPermission`, which the server works out and no role grants). The menus show the page to those people and nobody else, a person who may list the resource in no tenant is turned away from its route, and holding the page is a reason to have the place outside every tenant. A `page.permission` on the config is what the menus ask instead; the route's guard stays.

A page's list route asks List and its row route asks Read, each of its own route: the list's guard does not stand over the row. A person who may read a row opens it from a link drawn anywhere, whatever they may list, which matters where the list is a view and the row its table's (`rowsOf`), or where the link was drawn by a list across tenants.

**Icons.** Every icon the menu file and the pages name is typed `IconName` (from the types), the names of the Material Icons font the library ships, so a misspelled icon fails the build instead of drawing its letters. `bun run icons` writes the list again after a font update, and a test fails until it is run.

**Places.** A place is a tenant, or the place outside every tenant. The tenant the page is open in is the URL's: every tenant's page lives under the tenant segment the generated client names (`DomainRoutePath`, `tenants/:tenantID`). `tenantGuard` on that segment checks the tenant against the session's tenant list (asking the server once more when it is not there, since a deep link may arrive before the list), reads what the session holds there (the tenant's permission digest) and then opens it, before any page loads: a tenant's page knows its permissions the first time it draws, and a page already open in another tenant keeps that tenant's answers until the new tenant's are in; a tenant the session cannot reach is sent to the refusal page under the tenant's own URL (`refusedRoute`), which says 404 Not Found and nothing more, as the server's domain guard answers, and shows no tenant's id. A digest the server refuses to read (its 403 or 404) is refused the same way, with 404 Not Found. So is a tenant that has left the person's list since the list was read, a seat taken away while the person is signed in: the server answers such a tenant's digest with no entries, as it does for a tenant where the person holds nothing, so the client reads the list again for an empty digest, and a tenant the list names no more says 404 Not Found, on entering it and when its digest is read again while its page is open, with no reload; a tenant the list still names opens as one where the person holds nothing. A digest that cannot be read for any other reason (the server broke, or could not be reached) opens nothing either: the same page says "This page could not be loaded" with a Try again button that asks once more, under the address the person asked for, so reloading the browser asks again too; no page is drawn as if the person held nothing because a read failed. The page says so until the page that was asked for is drawn: once the read answers, a page the application loads when it is first asked for may still be on its way, and nothing else is said meanwhile, never 404 Not Found of a tenant the person is in. The same holds once a tenant's page is open: when its digest is read again (`AuthService.refreshPermissions`, after a change to what the person holds) and the read fails, the client keeps the answers it had, so the page is not drawn again as the page of a person who holds nothing, and the refusal page takes its place, with "This page could not be loaded" and Try again, or with 404 Not Found where the server refused. A seat taken away while a tenant's page is open is found by the page's next request, a move inside the tenant among them, which runs no guard: the server answers a request under a tenant the session does not reach with 404, the client reads the tenant's digest again before the request's caller hears of it, and where the tenant has left the list the refusal page takes the page's place with 404 Not Found, so no list or form is left saying the server's words about a tenant; a 404 for a record that is not there, in a tenant the person is still in, leaves the page as it is. The navigation that lands settles the rest, so no guard is needed for leaving. A person holds something outside every tenant when the application's menu file shows them something there: a page that lives there, or an action kept to it, that they may use. A grant there that no menu entry answers to (a record the application reads behind a tenant's page) is no place to work in, and an application whose menus hold nothing there has no such place. `outsideGuard` sends a person who holds nothing outside every tenant to the place they land in, instead of an empty page. The place switcher, beside the name, lists the place outside every tenant for a person who holds something there, then the tenants by name, under the application's word for a tenant, with a box to find one by name from eight places on. A tenant the person holds a seat in and cannot enter with this sign-in (the server's tenant list marks it `closed`, with the reason) is no place: the tenant guard refuses it like any tenant the session does not reach, and the switcher lists it under the places, apart, under "Closed to this sign-in", with a lock, its name and the server's sentence ("Acme admits only people who sign in through its own directory. You signed in with a password."), and nothing to open (`AuthService.closedDomains`, `PlaceService.closed`). Moving between tenants keeps the page; moving to or from the place outside every tenant opens that place's first page. A person lands where they last worked, remembered per application and per login; the first time, a person who holds something outside every tenant lands there and anyone else in their first tenant by name. A tenant the invitation names that is closed to this sign-in is passed over.

**A read that fails.** What a person holds is read from the server, and a read that fails is never taken for a person who holds nothing. Every reader says so in its own way. `AuthService.loadDigest` errors with what the read threw, and caches nothing. `AuthService.ensurePermission` errors too, and answers false only for a scope the server refuses (its 403 or 404, or a tenant that has left the person's list). `AuthService.digestUnread(domain?)` is true while a scope's last read failed and the cache holds no answer for it. The person's list of tenants is held to the same: `AuthService.loadDomains` errors with what the read threw and leaves the list as it was, never an empty list that would say the person is in no tenant; `AuthService.hasDomains()` says whether the list has been read, and `AuthService.domainsUnread()` is true while its last read failed and no list is held from before. Where a reader decides a page, the frame shows the failure where the page goes: `AuthorizationGuard`, `homeGuard` and `outsideGuard` send a navigation they cannot decide to the root address, carrying the address that was asked for (`unreadPageRedirect`, an `UnreadPage` as the navigation's `info`) and leaving the address bar alone, and `FrameComponent` draws "This page could not be loaded" with a Try again button in the page's place, and no page, while such a navigation is the one that landed, while the scope outside every tenant is unread or while the list of tenants is (`PlaceService.unread`). `tenantGuard` sends a tenant's page it cannot decide to the refusal page the same way, saying it could not be loaded: a tenant that is not on the list when the list cannot be read is never refused as 404 Not Found, since nothing says the person is not in it. Until the page that was asked for is in, the frame keeps saying what it said: a list read on the way to a tenant's page never draws the person as outside every tenant, and the refusal page under the frame never shows. Nothing is remembered as where the person works while the frame says the page could not be loaded, so a read that fails never moves where they land next. An application that draws its own shell instead of the frame reads the navigation's `info` the same way; without that, such a navigation lands on the application's root address.

## The login page

`<impulse-login-methods>` (`@impulseframework/resource-angular/auth-login-methods`) renders the sign-in methods
the server offers and owns the journey from the list to the session. On arrival it reads the
methods list through the application's client (`api.auth`, see the sign-in section of
@impulseframework/resource) and renders it: the password form when the list has a password method, asking
for the email address where the list says the username is one, and one button per redirect
method, in the server's order. Nothing it shows is named in the application, so the bundle is the
same in every environment and a method that is not registered has no button. The server's label is
the default for each method; `labels` overrides it by registration name, and nothing else about a
method is the page's to change. Everything around the methods, the branding, a manifest, a
forgotten-password link, is the page's, composed around the component:

```html
<mat-card>
  <mat-card-header><mat-card-title>Lodestar</mat-card-title></mat-card-header>
  <mat-card-content>
    <impulse-login-methods home="/" [labels]="{ google: 'the fleet directory' }" (signedIn)="go($event)" />
    <p class="hint">Ask the flight desk for an account.</p>
  </mat-card-content>
</mat-card>
```

```ts
export class LoginComponent {
  private idle = inject(IdleService);
  private router = inject(Router);

  constructor() {
    // The page ends no session: the component's first request, the methods list, primes the XSRF
    // cookie the sign-in's POST needs, and a session found standing is offered Continue or Sign out.
    this.idle.stop();
  }

  go(page: string): void {
    this.idle.start();
    void this.router.navigateByUrl(page);
  }
}
```

A password sign-in posts through the client, which reads the list again first so the POST carries a
live XSRF token even on a page left open past the cookie's life; the session established, the
component checks it through `AuthService` (loading the digest, the domains and the feature flags)
and emits `signedIn` with the router URL of the page to go to: the page the login guard turned away
from (`AuthService.redirectUrl`, read once), else `home`, which is the root unless the page names
another. An application with tenants leaves it the root, where `homeGuard` sends the person to
the place they last worked in; a page of the place outside every tenant named there would land
everyone who holds something in that place on it, wherever they last worked. The page navigates
there and starts what it starts on a sign-in. A redirect method sends the browser to the method's path, naming the same
page as the one to return to, resolved against the document's base; the server's callback brings
the browser back there signed in, or back to the login page with `?code=` for a refusal or
`?pending=` for a step that waits.

A page that offers its people as cards, as a demonstration does with its personas, fills the
password form with the component's `prefill(username, password)`; the person still presses Sign
in. The form's fields are bound to its inputs, and the component is drawn again only when
something of its own changes, so a field set from outside does not reach its input: `prefill`
sets both and has the form drawn.

A `returnUrl` in the login page's own URL names a browser path to return to, as the server sends

without one to the login page naming itself. The component keeps the address through the sign-in's

browser there with a full navigation instead of emitting `signedIn`, since no route of the
application draws it; the address the pending status reports after a redirect method's round trip
is followed the same way. Where the address came from decides, not its path: a page the guard
recorded is the application's and is routed to, one the server handed over is loaded. Only a path
in this application in canonical form is kept (`returnPath` in `@impulseframework/resource`, the server's
own rule), and never the login page, the sign-out page or another origin: anything else is dropped
and the sign-in lands as if the URL named nothing. The page needs nothing for this.

After a refusal, every redirect button asks the provider for its account chooser

The page ends no session on arrival, so a link to it signs nobody out: a bookmark, the back

sentence says "Your organization is already set up in this application. Ask its administrator to
invite you." and nothing of that tenant. An acceptance by a person already signed in that the
server refuses shows the server's sentence, the invitation still standing. A sign-up
link (`#signUp=<token>`) opens the same
account form in the list's place, and the list of a server whose password method offers sign-up
carries a "Create an account" step, which asks for an address and tells the person the link is on
its way, whatever the address's state. Under the password form the component draws "Forgot your
password?" only while the list names where a reset link is asked for (`passwordReset.request`),
which an administrator turns on and off in the running application: it asks for the address and
says a link is on its way if the address is an account's with a password, whatever its state. An
address sent too many reset links is refused with the wait and Send me a link stays disabled until
it has passed; the server counts reset links apart from sign-in codes, and so does the page, which
holds the reset form alone. Where an administrator turned resetting off after the page was drawn,
the form says so and to ask an administrator for a link. A
reset link (`#reset=<token>`), the person's own or one an administrator sent, opens a
form for the new password in the list's place, one `<impulse-new-password>` whose button stays
disabled until the server calls the password strong enough; once it is set the component says the person is signed out
everywhere and shows the list again with the username filled in, and nobody is signed in by it; a
password that changed while the person was choosing shows the server's sentence, the form staying. A
link to an address an administrator set (`#address=<token>`) shows a question first and posts
nothing on arrival; Confirm this email address posts it, with or without a session, and the
component names the address the account now holds. A confirmation link (`#verify=<token>`) is posted once a
session stands: on arrival when the page finds one, else after the sign-in it waits for. While it
waits, the component says so above whatever it shows: "Sign in to confirm your email address." A
redirect method's round trip reloads the application, so the token waits for it in the tab's session
storage and the method returns to this page with no token in the address, which is named in a
request line; a browser that refuses the storage keeps nothing, and the person opens the link again
once signed in. The
component then says the address is confirmed, or renders the server's refusal, and emits `signedIn`
on Continue. A link that has expired or was already used renders the server's words and the list.
On arrival the component holds the list back: a progress bar stands in its place and no form shows
until the reads have answered, so a person found signed in goes straight on to what the link asks
for (the address confirmed, the invitation to accept as they are, the pending step), or with
nothing in the URL is offered Continue and Sign out, and is never shown a form to fill in; the form
shows only to a person the session read finds signed out.
Canceling the account form or the sign-up shows the list again and emits `cancelled`.

## Signing out

`<impulse-sign-out>` (`@impulseframework/resource-angular/auth-sign-out`) is the page the application serves at
its sign-out route (`FRONTEND_SIGN_OUT_PATH`, `/logout` by default), the one place a navigation
ends the session. On arrival it stops the idle watch, ends the session through `AuthService.logout`
(the live session first, then the session's DELETE, then `LOGOUT_ACTION`) and forwards the browser
to `FRONTEND_LOGIN_PATH`, whatever the server answered, since a refusal there is a session it no
longer held. A sign-out control is a link to the route, `IdleService` sends the browser there when
the session times out, and the client's error hook leaves the page alone as it leaves the login
page: a 401 on either moves nothing and records nothing.

```ts
{ path: 'logout', loadComponent: () => import('@impulseframework/resource-angular/auth-sign-out').then((m) => m.SignOutComponent) }
```

```html
<a mat-stroked-button routerLink="/logout">Sign out</a>
```

## The email address

`<impulse-email-address>` (`@impulseframework/resource-angular/auth-email-address`) is the signed-in person's
email address for an account page. It reads the address from the session the `AuthService` last
checked (the address, whether the person confirmed it, and the address a directory asserted at a
sign-in, offered as a prefill while they hold none) and, where the methods list names the email
routes, offers to add, change or confirm it: the person types an address and the server mails it a
confirmation link; nothing is written until the link is followed on the login page, so an address
never attaches to an account its follower does not control, and the component says the link is on
its way whatever the address's state. A refusal (not an address; a mailbox sent too many links it
did not use, `too_many_emails` with the wait) is rendered in place, and the button stays disabled
until the wait has passed. A name that is no address is shown as no address: a development run
signs a persona in without a directory, and the session then carries the persona's login name
where a directory would have given an address.

```html
<impulse-email-address />
```

## A new password

`<impulse-new-password>` (`@impulseframework/resource-angular/auth-new-password`) is the one box
a person chooses a password in, on every page that sets one: the account page, and the login
page's password change, account form and reset link. It asks the server how strong the
password is while the person types (`api.auth.passwordStrength`) and draws the answer: a bar
that fills to where the password stands, a mark where the application's minimum sits, and
under them the server's sentence while the password falls short. It calculates nothing itself.
A control in the box shows what was typed, so there is no second box to type it again.
`strongEnough()` is true only while the server's last answer is about the text now in the box
and calls it strong enough: a page keeps its button disabled until then, and the server judges
the password again when it is set. One question is in flight at a time. Where the server holds
a browser that asked too often (429 with the wait), the component shows the server's sentence
and asks nothing until the wait has passed.

`username`, `personName` and `email` are what the page knows of the person. The server counts
them against the password, as it will when the password is set.

```html
<impulse-new-password
  label="New password"
  [username]="username"
  [personName]="name"
  [email]="email"
  [(password)]="newPassword" />
```

## The release

`<impulse-release>` (`@impulseframework/resource-angular/ui-release`) is the release the application runs, for
the login page and the frame's About pop-up. Every answer of the server names the release it was
built from in `X-Api-Version`, the client keeps the last one named (`client.serverRelease`, a store
read with `get()` and watched with `subscribe()`), and the component renders it: `v0.3.1` for a
release, a pull request's build as the pipeline names it, `dev` for a server built locally. Nothing
renders until the client's first answer, which on the login page is the methods list the login
component reads. When this build of the browser application names a release (`API_VERSION`) that is
not the server's, a tab kept open across a release until the update notice is taken, the line adds
which build the tab runs. Nothing about the application is named in it; the page puts its own name
beside it where it wants one.

```html
<impulse-release />
```

## The permissions card

`<impulse-permissions-card>` (`@impulseframework/resource-angular/ui-permissions-card`) is the card for what
a person may do: for each resource, what they hold of each permission. A page hands it the resources and
what the person holds on each, read from the permission digest; the card reads no session and asks the
server for nothing. Each answer is in words: `granted`, `terms apply` for a conditional grant (the server
decides row by row), `at certain times` for a grant that depends on the time alone, and a dash for nothing.

```html
<impulse-permissions-card heading="Your permissions" [resources]="rows()" />
```

```ts
private tenants = inject(TenantService);

// The digest's answer for each permission where the page is open: 'granted', 'conditional', 'conditionalOnTime', or nothing.
rows = computed<PermissionsCardResource[]>(() =>
  Object.values(Resources).map((resource) => ({
    name: resource,
    held: Object.fromEntries(READ_AND_WRITE.map((name) => [name, this.tenants.state(name as Permission, resource)])),
  })),
);
```

| Input         | What it is                                                                                                                                                       |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `resources`   | The rows: each resource's `name`, an optional `scope` written small beside it (a tenant's name, `global`), and `held`, the state of each permission by its name. |
| `permissions` | The permissions the card answers for, in order. `List`, `Read`, `Create`, `Update`, `Delete` unless the page names its own.                                      |
| `heading`     | The card's title. A card with no title and no line under it draws no header.                                                                                     |
| `subheading`  | The line under the title.                                                                                                                                        |
| `masked`      | The permissions a session's mask has removed. The card stripes them, heading and answers alike.                                                                  |

The card is laid out by its own width, not the window's. While its columns fit, it is a table with a
column for each permission. Where they do not, each resource is a block of its own: its name on a line
and its permissions under it, each named beside its answer. So the same card fits a phone and fits a wide
window where the page gives it a narrow column, and it has no frame of its own that scrolls sideways. The
card measures what its own table needs, so a page with longer names or more permissions changes over at
the width its content needs; a page sets no width and writes no layout for it. The change is drawn before
the browser paints the new width, so no frame shows a table too wide for the card, or blocks where a table
fits.

The card draws what it is handed, when it is handed it, so a page hands it rows it knows. Under
`tenantGuard` it does: the tenant's digest is read before a page under the tenant segment is drawn, so the
card's first drawing holds every row, and the line for a person who holds nothing is drawn only for a
person who holds nothing. A digest that cannot be read draws no page: the guard says the page could not
be loaded and offers to try again, so the line is never drawn because a read failed.

What a page writes inside the element is drawn under the table, in the same card. A card with no
resources says "You hold nothing here."; an element marked `permissionsCardEmpty` replaces those words:

```html
<impulse-permissions-card heading="Your permissions" [resources]="rows()">
  <span permissionsCardEmpty>No resources yet.</span>
  <p>Ask an administrator for anything you are missing.</p>
</impulse-permissions-card>
```

The skeletons' dashboards and Lodestar's service card are this card.

## User management

The pages that administer the people of an Auth are not a component an application composes:
they are routes the library builds from the generated description, the library's own list and
row pages over the lists and methods the server generates for the Auth (`identityRoutes` of
`@impulseframework/resource-angular/identity-pages`, under Core Concepts above). A console that
manages its staff and, by the generator program's declaration, its members asks for each Auth's
routes, the whole application's side at the root and a tenant's side where its tenant pages go:

```ts
...identityRoutes(apiDescriptor, resourceMeta, { auth: 'Crew', scope: 'global' }),
...identityRoutes(apiDescriptor, resourceMeta, { auth: 'Members', scope: 'global' }),
```

A page that asks one question of its own, with at most one field, can use the dialog the tokens
page uses: `askInDialog` of `@impulseframework/resource-angular/dialogs`.

A tenant's Sign-in page, which the tenanted skeletons carry, reads who the person is signed in
through from the session the `AuthService` last checked: `sessionInfo().directory` is the
organization's directory the session came through, its sign-in method and its connection
(`SessionDirectory`), and is absent for a session that came by password or with a personal
account. A tenant's directory is never typed in: the page offers a person who has one, and who may
set the tenant's directory, to make it the tenant's, with a create that names no directory, since
the server sets the one the session came through.

## Tokens

`<impulse-tokens>` (`@impulseframework/resource-angular/impulse-tokens`) is the signed-in person's tokens for the
application's machine outlets, for an account page. It configures itself from the `tokens` block
of the generated descriptor (see the tokens section of @impulseframework/resource): the routes, and the
machine outlets a token can be issued for. The page that composes it names the page; the component
carries no heading of its own. The frame composes it on its API keys page, under the heading "Your
API keys", which the person's menu opens in an application that issues tokens (see The frame). One sentence stands over the form: "A token lets a device or a
program of yours use this application as you. Name it for what it is for, so you know it in the
list." The form issues an application token by name for one outlet, chosen where the descriptor
lists several and fixed, and not mentioned, where it lists one; the token's value is shown once, in
a field with a Copy button (the clipboard where the browser offers one, the field's text selected
either way), with the sentence that it is not shown again. The table lists the person's live tokens
as the server serves them, newest first: an application token by its name, a device grant (the pair
a command-line client holds after the person approved its request) by the client's name and the
kind of each row, access or refresh, the outlet where there are several, when it was created, when
it expires and when it was last used, each to the minute ("Oct 28, 2026, 6:34 PM"). Each row ends
in a trash can that asks in a dialog ("Revoke nightly export?", "A device or a program using it
stops working at once.") and revokes in one call; revoking either row of a device grant revokes the
pair, and the dialog says so. A refusal is shown in place in the server's words, and the list is
read again after every write. Where the descriptor carries no block, the page says in one sentence
that the application issues no tokens for the signed-in person.

`<impulse-device-approval>` (the same entry) is the page where the person answers a command-line
client's request to act as them: the program printed a code and a link, and the person approves
or denies the request the code stands for. The component takes the code as `userCode`, else
reads it from the route's `userCode` query parameter, the link the program printed; with a code
it looks the request up and shows which program asks, for which outlet and until when, with
Approve and Deny; without one it asks for the code the program printed, in any case and spacing,
and looks it up on Continue. After a decision it says so; when no request waits on the code,
expired or already answered, it says so and asks for a code again.

```html
<impulse-tokens />
<impulse-device-approval />
<impulse-device-approval [userCode]="code" />
```

The device page is reached at the application's device verification path (`/device` by
default, what the program prints as its link) with `?userCode=XXXX-XXXX`, and belongs behind the
sign-in guard: a signed-out person who follows the link is sent to sign in and returns to the
page, code and all, once signed in. In the frame it is a child of `FrameComponent` beside the
places, not inside one, so the link lands on it whichever place the person works in.

## Modules Overview

- **`impulse-resource`**: The core module of the library. It contains the components and services related to dynamic page generation and data management.
- **`identity-pages`**: The pages over an Auth's people (the accounts, the roles held, the invitations, the sessions), built from the generated descriptor's identity block.
- **`impulse-tokens`**: The signed-in person's token page and the device approval page, configured from the generated descriptor's tokens block.
- **`auth-frame`**: The frame every signed-in page sits in: the bar, the menus from the application's menu file, the place switcher, the person's menu, the account and API keys pages, and the About pop-up.
- **`auth`**: This module provides authentication and authorization, including the login methods component, the email address component, route guards, and permission directives.
- **`ui`**: This module contains UI components and services, such as alerts, notifications, the update and maintenance notices, the theme picker with its service, and the card for what a person may do.
- **`utils`**: A collection of utility pipes and functions for various purposes.

## Development

### Building the Library

To build the library locally, copy the fonts it ships (from the two font packages the repository builds with, into `projects/resource-angular/fonts/`, a generated folder) and use the Angular CLI; the root build script does both:

```bash
bun run fonts && ng build resource-angular
```

### Running Tests

```bash
bun run test:angular             # once, as CI runs it
bun x ng test resource-angular   # watch mode
```

The specs run on Angular's unit-test builder (`@angular/build:unit-test`) with Vitest under jsdom
in Node; there is no browser to install. The builder initializes a library's TestBed zoneless, so a
spec drives the component itself: `TestBed.tick()` runs change detection and the effects behind it
(a resource's loader issues its request), the request is answered (`HttpTestingController`'s
`flush`, or the scripted transport below), and `await TestBed.inject(ApplicationRef).whenStable()`
settles the value. `fakeAsync`, `tick`, and `flush` from `@angular/core/testing` are not used:
Zone is not loaded, and nothing in the library advances timers.

#### The testing entry point

`@impulseframework/resource-angular/testing` exports `provideResourceTesting(options?)`: the providers a spec
of a component over the library needs. `RESOURCE_CLIENT` is provided over a scripted transport
(`scriptedTransport` from `@impulseframework/resource/testing`), so no request leaves the test and every
request is on record, and an empty router is provided, since the components read the route and
link to others. By default the client is `createClient` over an empty descriptor at `/api`; an
application passes its generated `createApi` as the `client` factory so the component under test
reads the descriptor its pages read, and its own transport to script the answers and read the
requests back:

```ts
import { ApplicationRef } from '@angular/core';
import { TestBed } from '@angular/core/testing';
import { scriptedTransport } from '@impulseframework/resource/testing';
import { provideResourceTesting } from '@impulseframework/resource-angular/testing';
import { createApi } from './zz_gen_api';
import { SquadronChannelComponent } from './squadron-channel.component';

describe('SquadronChannelComponent', () => {
  it('reads the squadron it is given and shows its callsign', async () => {
    const transport = scriptedTransport({ status: 200, body: { id: 'sq-1', callsign: 'Anvil Two' } });
    await TestBed.configureTestingModule({
      imports: [SquadronChannelComponent],
      providers: [provideResourceTesting({ transport, client: (t) => createApi({ baseUrl: '/api', transport: t }) })],
    }).compileComponents();

    const fixture = TestBed.createComponent(SquadronChannelComponent);
    fixture.componentRef.setInput('uuid', 'sq-1');
    fixture.detectChanges();
    await TestBed.inject(ApplicationRef).whenStable();

    expect(transport.requests.map((r) => r.url)).toEqual(['/api/squadrons/sq-1']);
    expect(fixture.nativeElement.textContent).toContain('Anvil Two');
  });
});
```

The client's error hook and error handler are not provided; a spec of the 401 redirect or the
uncaught-error notice uses `provideResourceClient` with its own transport. A component that reads
the page configuration from the route (`ActivatedRoute.snapshot.data['config']`) is given that
snapshot by its spec; the library's `resource-list-create.component.spec.ts` shows the shape. The
library's own creation specs (`*.component.spec.ts`) are the smallest examples.

### Known Issues

- **Contentful Dependency**: The library currently has a hard dependency on `@contentful/rich-text-types` due to the `CustomTypes.ContentfulDocument` type definition in the resource metadata. This means consumers of the library must have this package installed, even if they are not using this custom type.
