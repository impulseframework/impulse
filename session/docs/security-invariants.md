# Security invariants and where each is proven

This is the list of properties the session library must hold, with the test that proves
each one. A pull request that touches sessions, cookies or impersonation updates the row
it affects. "Layer" says where the proof lives; a property is only *proven* when a test
asserts the property itself, not merely that a call was made.

Layers, from the outside in:

| Layer | Package | What is real | Runs where |
| --- | --- | --- | --- |
| Seam suite | `internal/e2e` | A public session type on a chi router, real cookies over HTTPS, the public PostgreSQL and Spanner storage on the shipped migrations; the Auth scenarios run on both backends, under `/<backend>/` | Docker |
| Public surface | root `session` (`surface_test.go`) | Every handler and middleware on every session type, real cookies, mocked store | anywhere |
| Engine | `internal/basesession` | The shared middleware and impersonation lifecycle, mocked store and cookies | anywhere |
| Storage contract | `sessionstorage` | The public store over a generated mock of the driver | anywhere |
| Driver conformance | `sessionstorage/internal/drivertest`, run by both drivers | Real PostgreSQL and Spanner containers, one case table | Docker |

Known and accepted around a sign-in on proof of a password (A24, U35). Three narrow
gaps stay as they are, written down here so that each is a decision and not a surprise:

- **An invitation accepted by a sign-in that is then refused on its proof stays
  accepted.** A sign-in's first transaction commits before the transaction that
  inserts the session: the resolution of a directory identity with what it gives, and
  the acceptance of the invitation a sign-in carries, a password sign-in's among them.
  Each of the two compares the proof on the user row it reads, so a password changed,
  reset or removed before the first leaves the invitation standing (U50). One that
  commits between the two is refused (`ErrPasswordChanged`) with the invitation
  consumed and its roles given, as a sign-in the policy refuses leaves them. No session
  results, and the roles are the invited account's.
- **The session a person's own change continues in is inserted after the change's
  transaction.** `ChangeUserPassword` writes the password and ends every session of
  the user in one transaction (A23); the session the person goes on in is inserted
  next, in a transaction of its own and on no proof. A password set through a reset
  link or a removal that commits between the two ends the sessions before that one is
  there, so it outlives that write: one session, of the person who had just proved the
  password it replaced, in the browser that made the change.
- **A completion refused on its proof leaves the pending sign-in consumed.** A pending
  sign-in is consumed before its completion signs in, so a copy of the cookies
  completes nothing (U28). A completion that then finds the password changed is
  refused as a wrong password is (U35) and the row is spent: the person signs in
  again, with the password they now hold.
